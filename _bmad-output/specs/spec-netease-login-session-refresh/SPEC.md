# 网易云登录会话刷新与失效恢复

## Why

当前服务使用 `MUSIC_U` 获取歌曲 URL，并在 Cookie 失效后尝试刷新 token；最近刷新被网易云拒绝，即使 `.env` 已替换为新的 `MUSIC_U` 也没有恢复。根因排查显示，持久化 Cookie 可能继续覆盖 `.env`，而单独的 `MUSIC_U` 也不能代表完整、可刷新的登录会话。服务需要可靠识别实际使用的会话，区分可刷新与必须重新登录的状态，并安全保存网易云返回的新 Cookie。

## Capabilities

- **CAP-1**
  - **intent:** 服务能明确选择并使用一份完整的最新登录 Cookie，避免旧持久化会话静默覆盖用户提供的新凭证。
  - **success:** 通过显式会话替换后，脱敏诊断显示来源、字段完整性和新会话指纹；播放请求与账号校验使用同一份会话中的 `MUSIC_U` 和 `__csrf`。

- **CAP-2**
  - **intent:** 服务能判断登录会话和 token 刷新结果是否真正可用。
  - **success:** 刷新和账号校验同时区分 HTTP 状态、网易云业务 `code`、账号信息、关键 Cookie 和播放权限；HTTP 200 或单个非空字段不能单独判定成功。

- **CAP-3**
  - **intent:** 服务能在会话仍可刷新时续期并保存网易云返回的完整 Cookie。
  - **success:** 有效刷新返回的 `Set-Cookie` 被合并为完整 Cookie 并原子保存；并发刷新只产生一次上游请求；失败刷新不会覆盖最后一个已知可用会话。持久化 `MUSIC_U` 经账号接口确认失效后，服务会尝试 `.env` 中的 `MUSIC_U`，并且只有刷新响应再次通过账号校验后才写盘。

- **CAP-4**
  - **intent:** 服务能识别无法通过 token refresh 恢复的登录状态并引导重新登录。
  - **success:** 对刷新拒绝、账号校验失败、会话来源不支持刷新和缺少关键字段分别返回稳定的状态分类与下一步动作，且不会无限重试。

- **CAP-5**
  - **intent:** 服务能提供不泄露凭证的登录会话诊断。
  - **success:** 运维可以看到会话来源、字段存在性、长度或不可逆短指纹、最后更新时间、刷新分类和账号校验结果；日志、文档和接口响应不包含 `MUSIC_U`、Cookie 原文或带鉴权参数的音频 URL。

## Constraints

- 登录 Cookie 是敏感凭证；只允许记录存在性、长度和不可逆短指纹，禁止保存或输出原值。
- 现有播放链路使用 EAPI 登录刷新请求；协议或请求头变化必须保持播放调用兼容，并用脱敏的真实响应或可复现样本验证。
- 持久化会话必须避免半写入和并发覆盖；刷新失败必须保留最后一个已知会话。
- 不能把单独的 `MUSIC_U` 视为完整登录会话；`__csrf`、`NMTID`、`MUSIC_R_U`、`MUSIC_R_T`、`MUSIC_SNS`、设备指纹和登录来源的作用必须通过验证决定。
- 当前没有用户提供的刷新失败响应和登录来源记录；无法确认的上游原因必须保持为开放问题。
- 本次实现允许把 `.env` 中的单独 `MUSIC_U` 作为失效持久化会话的刷新候选；这只能验证兜底链路，不能证明单独 `MUSIC_U` 在所有登录来源下都能恢复完整会话。

## Non-goals

- 本次规格不实现网易云账号密码、二维码或短信登录流程。
- 本次规格不保证已失效或不支持续期的会话可以仅凭 `MUSIC_U` 恢复。
- 本次规格不更换音频来源、不实现解灰、不代理音频流，也不扩大其他音乐平台范围。
- 本次规格不把完整 Cookie 暴露到公共管理接口或日志。

## Success signal

管理员可以显式导入一份完整 Cookie，服务能确认当前实际使用的会话并完成账号校验；会话可刷新时自动续期且播放继续可用，会话不可刷新时在有限重试后明确提示重新登录及原因分类。使用旧持久化 Cookie、缺少 `__csrf` 或刷新失败时，不会再静默覆盖新凭证或报告假成功。

## Assumptions

- 用户希望继续使用服务端共享账号和自动刷新，而不是每次请求由调用方携带完整 Cookie。
- 当前运行时只有在 `/mnt/account/netease` 目录已存在时才选择 `/mnt` 路径；否则使用项目 `data/account/netease/cookie.json`，避免仅因 `/mnt` 存在而忽略项目数据。本机项目数据文件中的 `MUSIC_U` 与 `.env` 值不同，但不能据此断定上游账号状态。
- 参考项目 `api-enhanced` v4.41.1 仍使用 `/api/login/token/refresh`，未发现仅替换 `MUSIC_U` 的新刷新机制。

## Open Questions

- 新的 `MUSIC_U` 是通过网页版、二维码、手机号/邮箱登录，还是客户端抓取得到的？不同登录来源可能有不同的刷新限制。
- 刷新失败时的 HTTP 状态、业务 `code`、`msg`、`Set-Cookie` 和响应头是什么？脱敏样本才能区分凭证失效、CSRF 缺失、请求指纹、IP 风控和接口策略变化。
- 是否允许提供一次显式的会话替换操作，把 `.env` 或管理接口中的完整 Cookie 原子导入持久化存储？
